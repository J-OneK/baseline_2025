## 当前主分支的完整推荐

给定用户可见历史，冻结的一层 InfoNCE 先从约 154 万广告中取精确 Top-500，同时按历史的 102/122 匿名属性和 81 号向量相似度各补最多 5 个冷启动与长尾候选。合并维持 500 条。每条候选的原融合分由标准化内积分数和内容 MLP logit 组成。新 DCN V2 加上学习的残差，按总分输出十条。

训练来源为 24,000 名用户；两个种子分别有 3,943 和 4,270 份实际候选列表包含目标点击。每份完整 500 条上做交叉熵，输入增加来源标记、相似历史的点击或曝光类型、时间差等特征。5,000 人开发集依次比较冻结分数、基础列表 MLP、通道 MLP、通道 DCN V2。锁定第 5 轮、残差系数 1 的 DCN V2，再用 6,000 名独立用户确认。

| 确认指标，两种子均值 | 原融合 | 重排 |
|---|---:|---:|
| HR@10 | 2.233% | 2.917% |
| NDCG@10 | 0.01225 | 0.01602 |

同候选排序的 HR@10 差为 +0.683 个百分点，95% 配对区间 +0.383～+0.992 个百分点。新排序净增的 82 次命中有 76 次来自头部。两位不同用户的长尾目标由辅助通道补入后进入前十；确认集里唯一进前十的冷启动目标来自原召回。加入辅助候选令冷启动 Recall@500 从 8.735% 到 9.835%，同时整体 Recall@500 从 16.975% 到 16.867%。

现场演示运行 `python scripts/recommend_channel_rank.py --device cpu --rid 134009 --show-target`。该用户的长尾目标在原 500 条以外，补入后排第 492，重排后第 6。 [运行入口](ranking_extension.md) · [方案、配置、案例与完整结果](../reports/channel_rank/README.md)

## 1. 项目背景与问题

### 1.1 要完成什么任务

在广告推荐场景中，给定一个用户的静态属性及截至当前时刻已经发生的广告行为，从一个很大的广告目录中寻找可能相关的广告。

本项目将任务落到一个可运行的召回链路：

```text
公开 Parquet 数据
  → 清洗、按用户时间留出、ID与特征对齐
  → 用户信息＋广告行为历史
  → 因果 Transformer 生成32维用户查询 q
  → 与广告向量 v 做内积
  → 过滤历史广告、无效项、重复项
  → 返回广告 OID

稳定主链路：向量导出 → 持久化 Faiss → Top-10 演示
辅助研究：原主 Top-500＋零点击长尾新提议 → 固定500候选
```

训练不是直接学习“这个曝光是否会点击”的完整 CTR 预估器。当前主任务是**下一事件为点击的位置上的广告匹配学习**，再以留出的广告点击检查召回能力。模型输出也不是经过校准的点击概率。

### 1.2 项目来源与自己的工作

数据来自 [TAAC2025/TencentGR-1M](https://huggingface.co/datasets/TAAC2025/TencentGR-1M)。上游是 [腾讯广告算法大赛官方基线](https://github.com/TencentAdvertisingAlgorithmCompetition/baseline_2025)，其模型基于 SASRec 风格的序列建模。相关背景见 [TAAC2025 论文](https://arxiv.org/html/2604.04976v1)。

当前项目复用了上游的注意力与前馈模块，随后补齐或重新组织了：

- 向量化的数据准备、特征查表和张量接口。
- 明确的逐用户时间切分、首次出现点击留出和候选目录协议。
- 监督策略、BCE/InfoNCE、负样本数量及动作输入的对照。
- 验证选型、三种子确认、分桶分析及配对区间。
- 向量导出、Faiss 持久化、身份校验、历史过滤和推荐 CLI。
- 冷尾训练信号诊断、失败尝试及最终的辅助召回实验。

因此，准确的项目定位是**基于公开广告数据与官方基线的序列召回、受控实验及检索工程项目**。本项目没有实现论文中的全部生成式推荐路线，也没有实现语义ID自回归生成。

来源：[上游说明](upstream_baseline_zh.md)、[代码导读](code_walkthrough.md)、[版本范围](release.md)。

### 1.3 三个具体问题

| 问题 | 处理方向 | 核验方式 |
|---|---|---|
| 曝光和点击混在下一事件训练中，目标是否匹配最终点击任务？ | 比较监督位置、损失及负采样预算 | 同一开发协议选型，再进行三种子测试 |
| 270万候选下逐项打分开销较大，近似检索能否保持原模型语义？ | Faiss，验证 HNSW 的几何与参数 | 对照同模型精确 Top-10，测重合率和检索耗时 |
| 总体命中集中在头部，零点击长尾难召回 | 先诊断，再增加面向特定子群的辅助通道 | 固定500预算，报告新增、丢失、分桶和不确定性 |

## 2. 数据来源、规模与使用范围

### 2.1 官方公开数据与本地实际数据

官方数据是脱敏的腾讯广告日志，使用 Parquet 存储。公开卡片说明约100万条用户序列，每条最多100个事件；本地 Parquet 元数据确认 `seq` 和 `user_feat` 各有 **1,001,845行**。

| 数据部分 | 本地记录规模 | 含义 |
|---|---:|---|
| `seq` | 1,001,845条用户序列 | 每条包含广告、行为、时间戳 |
| `user_feat` | 1,001,845行 | 用户匿名静态属性 |
| `item_feat` | 4,783,154行 | 出现在公开序列中的广告属性 |
| 官方 `candidate` | 660,000行 | 比赛候选集合，不是本项目离线评估目录 |
| `mm_emb` | 81～86共6族表示 | 向量维度和覆盖不同，主项目只读取81 |
| `indexer.pkl` | ID与属性编码映射 | OID、RID及官方类别编码之间的关系 |

来源：[官方数据卡](https://huggingface.co/datasets/TAAC2025/TencentGR-1M)、本地 [数据说明](../TencentGR-1M/README.md)。这里报告的是公开表行数，不把论文的平均序列长度反乘成未经核对的精确总事件数。

### 2.2 “下载了128G”与“训练用了多少”要分开

本机 `TencentGR-1M` 目录的 `du -sh` 显示约 **128G**。按文件逻辑字节统计：

| 范围 | 字节数 | 解释 |
|---|---:|---|
| 包括下载缓存的目录 | 137,134,002,388 B，约127.716 GiB | 本机下载占用范围，不是训练张量规模 |
| 排除下载缓存的文件 | 137,066,125,345 B，约127.653 GiB | 原始数据与附带文件 |
| 当前处理流程相关Parquet及indexer合计 | 2,153,585,596 B，约2.006 GiB | 序列、用户/广告属性、candidate、indexer和81，不含README等附带文件 |

绝大部分下载体积来自高维向量族。当前主模型**没有读取82～86，也没有训练这些向量的上游编码器**。模型参数、训练缓存和索引属于另外生成的产物，不能与下载大小混为一谈。

### 2.3 当前实验实际使用的规模

主模型先在较小开发缓存上选型，再扩大到确认规模：

| 项目 | 小规模开发 | 主模型确认 |
|---|---:|---:|
| 随机抽样用户上限 | 100,000 | 300,000 |
| 清洗后有效用户 | 93,586 | **280,985** |
| 固定候选广告 | 1,538,730 | **2,708,122** |
| 训练前缀事件 | 6,455,291 | **19,361,659** |
| 训练出现过的广告 | 1,330,423 | **2,385,886** |
| 每个评估split的用户数 | 2,000 | **10,000** |

确认规模抽到的300,000名用户共有 **27,012,974条原始事件**；其中19,015名用户不满足留出规则被排除。保留用户的完整截断序列共有25,617,081条事件，进一步截取训练前缀后才是19,361,659条训练事件。

训练前缀动作分布：

| 内部动作 | 含义 | 事件数 |
|---|---|---:|
| 1 | 曝光 | 17,149,332 |
| 2 | 点击 | 2,050,483 |
| 3 | 未知 | 161,844 |
| 合计 | 全部训练上下文 | 19,361,659 |

这也解释了为什么“训练事件数”“有效监督位置数”“点击正目标数”不是同一个数字。

依据：本机 `artifacts/baseline/data/metadata.json`、`artifacts/objective_study/scale_data/metadata.json`，以及可随仓库阅读的 [数据审计](../reports/objective_study/scale_data_audit.json)。

## 3. 原始数据格式与四层编号

### 3.1 原始行为与属性

下面是**结构教学样例，不是真实用户记录**：

```json
{
  "user_id": 42,
  "seq": [
    {"item_id": 101, "timestamp": 1000, "action_type": 0},
    {"item_id": 202, "timestamp": 1010, "action_type": 1},
    {"item_id": 303, "timestamp": 1020, "action_type": null}
  ]
}
```

原始动作 `0=曝光、1=点击`。当前缓存统一为：

- `0`：padding或用户token位置的动作占位。
- `1`：曝光。
- `2`：点击。
- `3`：未知，保留为历史上下文，但不提供监督标签。

字段分组为：

```python
ITEM_FIELDS = ['100', '117', '118', '101', '102', '119', '120',
               '114', '112', '121', '115', '122', '116']
USER_FIELDS = ['103', '104', '105', '109']
USER_ARRAY_FIELDS = ['106', '107', '108', '110']
PROTOCOL_VERSION = 2
```

前3组是公开表中的匿名特征字段；`PROTOCOL_VERSION` 是本项目的数据准备协议版本，不是原始数据特征。

广告和用户单值属性是整数编码；用户多值属性是整数列表。字段编号不能被解释成已知的品类、职业或年龄。缺失值和列表中的空元素需要单独处理。

### 3.2 81号向量是什么

“81”是官方表示家族编号，**32才是维度**。原表以 `anonymous_cid` 表示广告OID，`emb` 是长度32的数值列表。

论文第3.3节Table 3将81描述为文本侧的 Bert-finetune 表示。当前项目直接读取提供的向量，经 `Linear(32,32)` 接入广告编码器；没有读取原始广告文本，也没有重新训练文本模型。[论文对应章节](https://arxiv.org/html/2604.04976v1#S3.SS3)

缺失向量填0，并保存内容存在标志用于诊断。当前候选目录中81覆盖率约 **95.1988%**。输入81接近单位范数，不意味着投影、属性拼接和ReLU之后的广告输出仍是单位向量。

### 3.3 四层编号

```text
广告原始OID
   ↓ indexer.pkl
公开数据中的RID
   ↓ catalog_rids.npy
当前实验的local ID
   ↓ item_id_lookup.npy
ID Embedding的行号
```

| 编号 | 用途 | 容易混淆的地方 |
|---|---|---|
| OID | 原始广告身份、内容表关联、最终推荐输出 | 不一定能直接当数组下标 |
| RID | 公开数据重编号，出现在seq与item_feat | 是公共编码，不等于当前实验local ID |
| local ID | 当前固定目录中的紧凑下标 | 0保留给padding |
| Embedding行号 | 只给训练可见广告分配独立行 | 冷广告可能有local ID，却共享OOV行0 |

手算例子：

```text
catalog_rids = [0, 2, 6, 9]
train_counts = [0, 3, 0, 7]

训练出现的位置是local 1和local 3
按local顺序给它们编号1、2：
item_id_lookup = [0, 1, 0, 2]
```

这里的1、2表示“第一个、第二个训练可见广告”，不是频次3、7的变换。RID6有local2，但没有训练事件，所以ID使用行0；RID9有local3，ID使用行2。

主目录完整非padding索引中，Faiss行0对应local1，可以加1还原；辅助目录是非连续子集，必须用显式映射，后文会再次说明。

## 4. 清洗、时间切分与评估假设

### 4.1 clean_and_split的处理顺序

[`clean_and_split()`](../taac_retrieval/prepare.py) 执行：

1. 过滤空事件、缺少有效广告ID或时间戳的记录。
2. 按时间稳定排序，只保留最后100条事件。
3. 在该保留窗口内寻找“广告此前未出现过”的点击。
4. 要求目标前严格更早的历史至少有5条。
5. 最后一个合格点击作为测试目标。
6. 在更早且时间严格小于测试目标的合格点击里，选最后一个作为验证目标。
7. 训练和验证输入都截止于验证目标之前；测试输入截止于测试目标之前。

首次出现的判断同时排除了“前面已经曝光过，后面才点击同一广告”的目标。原因是公开数据没有提供可供当前代码使用的曝光—点击归因ID，而推断又会过滤历史广告，必须避免答案在评估时被过滤。

“首次出现”只针对保留的最多100条历史，不代表用户一生第一次见到该广告。

### 4.2 严格时间与两次留出

假设验证目标广告B发生在 `t=20`，测试目标C发生在 `t=30`：

| 阶段 | 可见行为 | 是否更新参数 |
|---|---|---|
| 训练 | `t<20` | 是 |
| 验证 | `t<20` | 否，选epoch |
| 测试 | `t<30` | 否，锁模型后评估 |

测试输入可以包含较早的验证点击B，这属于当时已经发生的历史；参数仍只由训练前缀更新。相同时间戳的事件不被强行排列为因果先后，使用 `searchsorted(..., side='left')` 确定严格更早的截止点。

### 4.3 为什么没有直接使用官方660,000候选

官方候选集合对应比赛任务，本地任务重新按用户留出点击，其目标不一定都位于官方候选中。

本机元数据对保留用户目标的审计显示，官方候选对本地验证目标覆盖约73.35%，对测试目标覆盖约81.01%。这不是模型的召回成绩，而是“正确答案是否在目录里”。

因此，本地评估固定使用**保留公开序列中全部广告的并集**，共2,708,122条，所有模型使用相同目录，目录构建不按点击标签筛选广告。

### 4.4 公共静态目录假设，用大白话解释

实验允许提前知道公开快照里有哪些广告ID、属性及81向量；但是每名用户的留出行为不能进入其训练历史。

这相当于提前拿到了“商品目录”，没有把“这个用户后来会选哪个商品”当作训练样本。本项目仍然不是严格的生产未来回测：

- 没有让所有用户共享一个全局时间截止点。
- 各用户的历史时段可能重叠。
- 目录包含本次训练未出现的广告。
- 使用的是官方提供的预提取向量，其上游训练不能被本项目自行解释成严格的全局时间隔离。

因此报告使用 `transductive public static catalog`、逐用户时间留出的表述，不称为未来新广告上线回测。

## 5. 特征编码与缓存

### 5.1 广告属性词表

ID和广告属性词表只在训练出现过的广告上拟合。假设字段100的训练可见原值为 `[4,9,4]`：

```text
加上缺失/OOV值0：vocabulary = [0,4,9]

0 → 行0
4 → 行1
9 → 行2
12 → 训练词表未见 → 行0

feature_sizes['100'] = 3
```

这是把离散类别转换成紧凑行号，不是数值大小归一化。广告ID冷启动与属性OOV也不相同：新广告可以没有独立ID行，却拥有训练已经见过的属性值，从而复用属性参数。

### 5.2 用户属性

保留用户按RID排序，映射到从1开始的内部用户行号，第0行保留为空白。4个单值字段保存为 `user_sparse.npy`；4个多值字段分别保存为 `user_array_106.npy` 等。

用户属性沿用官方类别编码，没有再做广告侧那种基于训练可见广告的词表拟合。多值字段去除空元素、补0；模型将有效属性Embedding**求和**，不是取平均。

例如 `[1,4,0]` 编码为 `e₁+e₄+0`，输出仍为32维。当前评估面向同一训练人口中的留出行为，不能据此声称用户ID模型已经验证了全新用户冷启动。

## 6. 主模型结构与完整样例

### 6.1 广告编码器

广告有15块32维表示：

1. 一个训练可见广告ID Embedding。
2. 13个匿名离散属性各自的 Embedding。
3. 一个81向量的线性投影。

令 `C` 为本批广告数，广告编码过程为：

$$
z_i=[e_{\mathrm{ID},i};e_{100,i};\cdots;e_{116,i};P m_{81,i}+b_P]
\in\mathbb{R}^{480},
$$

$$
v_i=\operatorname{ReLU}(W_{\mathrm{item}}z_i+b_{\mathrm{item}})
\in\mathbb{R}^{32}.
$$

分号表示拼接，所以是 `[C,480]→[C,32]`，不是把15个向量直接相加。实际字段拼接顺序以 `ITEM_FIELDS` 为准。

广告ID OOV行为与padding也要区分：local0是无效广告，最终输出整体乘0；真正冷广告有非零local ID，只是ID块为0，其他属性、81及偏置仍可产生非零广告向量。

### 6.2 用户token编码器

用户输入有9块32维向量：

- 1个用户ID Embedding。
- 4个用户单值属性 Embedding。
- 4个用户多值字段内的 Embedding求和结果。

$$
u=\operatorname{ReLU}
\left(W_{\mathrm{user}}[e_{\mathrm{uid}};e_{103};e_{104};e_{105};e_{109};
a_{106};a_{107};a_{108};a_{110}]+b_{\mathrm{user}}\right).
$$

因此为 `[B,288]→[B,32]`。这里 `B` 是用户batch数，和广告编码batch数 `C` 不是同一个概念。

### 6.3 把用户与广告放进同一序列

一名用户的一次输入可以理解为：

```text
[左侧PAD..., 用户token, 广告1, 广告2, ..., 最近广告]
```

`kinds` 区分位置类型：

- 0：padding。
- 1：广告。
- 2：用户token。

用户token位置放用户向量，广告位置放广告向量；加上位置编码，得到序列输入：

$$
X_t=\operatorname{Dropout}\left(\sqrt{32}\,E_t+
\operatorname{PositionEmbedding}(p_t)\right).
$$

位置编号对有效token累加，左侧padding不占有效位置。主模型不额外加入动作Embedding；曝光/未知广告仍以广告token形式进入上下文。

### 6.4 因果Transformer

主干使用1层、1个注意力头、32维隐藏表示：

$$
Q=XW_Q,\quad K=XW_K,\quad V=XW_V,
$$

$$
\operatorname{Attention}(Q,K,V)=
\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{32}}+M\right)V.
$$

`M` 屏蔽未来和padding key。有效位置只能读取自身及更早有效位置；padding query额外允许关注自身，避免整行被屏蔽后的softmax产生NaN，随后输出再乘有效位掩码归零。

当前代码使用注意力残差、LayerNorm、逐位置前馈残差和最终LayerNorm。前馈是 `32→32→32` 的kernel-size=1卷积实现，并未使用常见的4倍扩张宽度。

`FlashMultiHeadAttention` 是复用模块的类名，内部优先调用 PyTorch `scaled_dot_product_attention`；具体执行内核由PyTorch和硬件条件决定，不能仅凭类名宣称已获得某个Flash内核的速度收益。

训练得到 `[B,101,32]` 的每位置状态；预测时取最后有效历史位置：

$$
q_u=\operatorname{SequenceEncoder}(u,H_u)_{\mathrm{last}}
\in\mathbb{R}^{32},\qquad s(u,i)=q_u^\top v_i.
$$

主通道使用**原始内积**，没有先把最终向量全部归一化成余弦。

来源：[SequenceRetriever](../taac_retrieval/model.py)、[上游注意力和前馈模块](../model.py)。

### 6.5 用一条具体序列贯穿训练与评估

以下为 [HTML教学演示](project_masterclass.html) 中实际生成并执行过的**合成数据**，不是公开数据用户效果证据。为便于读，历史上限缩为10：

| 位置 | 广告 | 原始动作 | 时间 |
|---:|---:|---|---:|
| 0 | 1 | 曝光 | 10 |
| 1 | 2 | 点击 | 20 |
| 2 | 3 | 未知 | 30 |
| 3 | 4 | 曝光 | 40 |
| 4 | 5 | 曝光 | 50 |
| 5 | 6 | 点击 | 60 |
| 6 | 6 | 再次点击 | 70 |
| 7 | 7 | 曝光 | 80 |
| 8 | 8 | 点击 | 90 |
| 9 | 9 | 曝光 | 100 |

`min_history=5` 时：

- 验证目标是广告6，训练/验证历史都是广告 `[1,2,3,4,5]`。
- 广告6在位置6重复出现，因此不再作为另一个首次出现目标。
- 测试目标是广告8；测试输入包含位置0～7的行为。
- 位置9的广告9不会因为存在于公开完整序列就进入该用户的训练输入。

训练是移位预测：

```text
输入：    [用户token, 1, 2, 3, 4]
下一目标：[1,        2, 3, 4, 5]
目标动作：[曝光,   点击,未知,曝光,曝光]
主loss： [不选,    选中,不选,不选,不选]
```

因此，**输入广告1是曝光，但它预测的广告2是点击，其状态参与主损失**；输入广告2虽然是点击，它预测的下一广告3是未知事件，该位置不参与主损失。

验证时则把完整可见前缀 `[用户token,1,2,3,4,5]` 编码为查询，检索目标广告6。训练位置监督与验证整条历史查询是两个不同环节。

来源：[样本构造](../taac_retrieval/data.py)、[实际合成执行记录](tutorial_parts/demo_trace.json)。

## 7. 监督、负采样与训练

### 7.1 点击mask选择的是目标位置

主模型的 `supervision_weights(target_actions, 'click_infonce')` 返回 `target_actions==2`：

```python
weights = supervision_weights(batch['target_actions'], 'click_infonce')
mask = (batch['positive'] != 0) & (weights > 0)
states = model.encode_history(
    batch['items'], batch['kinds'], batch['actions'], batch['user']
)[mask]
```

`positive!=0` 排除padding目标；目标动作是点击才保留。这里不是对输入 `actions` 直接筛选，也不是跳过曝光、把每个输入都连接到更远的下一次点击。

当前确认规模每轮点击监督位置为 **2,050,483**。一次batch虽然包含128名用户，但每人可能贡献多个点击位置，因此有效位置数 `M` 不固定，通常也不等于128。

### 7.2 负样本如何构造

负采样池为 `train_counts>0` 的2,385,886条广告。对每个有效点击位置：

1. 在池中均匀、有放回抽取64条广告。
2. 检查是否出现在该用户整段训练前缀。
3. 如果冲突，重新抽取冲突位置，直到合法。
4. 不查询该用户的验证/测试目标来筛负例。

```python
positive = batch['positive'][mask]                # [M]
row_indices = torch.where(mask)[0]              # [M]
negative = sample_negatives(
    negative_pool,
    batch['seen'][row_indices],
    (count, 64),
    negative_generator,
)                                               # [M,64]
```

几个边界：

- 有放回意味着64条里可能重复，不是64个保证不同的广告。
- 这些是采样负候选，不等于已经证明用户讨厌的广告。
- 排除的是整段训练前缀，而非只排当前输入位置之前的事件；这是离线训练的去假负例约定，不读取留出行为。
- 冷广告没有训练事件，因此不在该负池中。
- 负采样数量占比不能直接解释为梯度贡献占比。

来源：[sample_negatives](../taac_retrieval/data.py)。

### 7.3 InfoNCE-64的计算

对有效位置 `t`，真实点击广告得分 `s_t^+`，64个负候选得分 `s_{t,k}^-`：

$$
p_t^+=
\frac{\exp(s_t^+/\tau)}
{\exp(s_t^+/\tau)+\sum_{k=1}^{64}\exp(s_{t,k}^-/\tau)},
$$

$$
\mathcal L=
-\frac1M\sum_{t=1}^{M}\log p_t^+,\qquad \tau=1.
$$

实际实现将正例放到第0列：

```python
logits = torch.cat([positive.unsqueeze(-1), negative], dim=-1) / temperature
loss = F.cross_entropy(
    logits,
    torch.zeros(len(positive), dtype=torch.long, device=positive.device),
)
```

标签0指“65列中第0列是真实点击”，不是把padding广告当正例。这个softmax是在采样候选内形成的相对概率，不是全目录点击概率。

正例分数梯度为 `(p⁺−1)/τ`，负例梯度为 `p⁻/τ`；梯度下降会提高正例的相对得分、压低负候选得分。更新包含用户、广告属性/ID、81投影和Transformer等参与路径，官方提供的原始81数组本身是固定特征。

来源：[objectives.py](../taac_retrieval/objectives.py)。

## 8. 精确评估与指标

### 8.1 精确全库检索

先编码固定目录内全部广告，再对每个用户查询计算内积，过滤历史广告，按原始分数取Top-K。为了省内存，将目录分块，维护当前前K：

$$
\operatorname{TopK}(A\cup B)=
\operatorname{TopK}(\operatorname{TopK}(A)\cup\operatorname{TopK}(B)).
$$

块内排在K名以后的广告，不可能进入全局Top-K，因此分块仍是精确检索；并没有通过少算广告来降低评估难度。同分边界的具体ID次序仍取决于实现的tie处理。

### 8.2 HR、Recall与NDCG

每个用户只有一个留出目标，`r_u` 是过滤后的一基排名：

$$
\operatorname{HR@K}=\operatorname{Recall@K}
=\frac1U\sum_u\mathbf1[r_u\le K].
$$

$$
\operatorname{NDCG@K}
=\frac1U\sum_u
\frac{\mathbf1[r_u\le K]}{\log_2(r_u+1)}.
$$

单目标理想DCG为1。目标在第3名时NDCG为 `1/log₂4=0.5`；第11名时，HR@10和NDCG@10都为0。

**HR@10与Recall@500不是两个随意替换的命名。** 在同一K、单目标协议下HR与Recall相同；K从10变成500，衡量的候选范围已经变化。

| 指标 | 回答的问题 |
|---|---|
| HR@10 | 目标是否进入最终前十 |
| NDCG@10 | 命中且在前十里排得多靠前 |
| Recall@100/500 | 给后续阶段留下目标的候选覆盖空间 |
| ANN Recall@10 | 近似结果与同模型精确Top-10的ID重合程度 |
| 新增/丢失命中 | 辅助候选相对主列表补回什么、挤掉什么 |

来源：[metrics.py](../taac_retrieval/metrics.py)、[coverage.py](../taac_retrieval/coverage.py)。

### 8.3 分桶与配对区间

频次桶基于目标广告在所有训练前缀中的事件数：

- `cold_0`：0次。
- `tail_1_5`：1～5次。
- `mid_6_50`：6～50次。
- `head_gt50`：大于50次。

主实验保留逐用户预测，使用配对bootstrap重采样用户和已有模型种子，再计算两方案差值。主实验用2,000次、随机种子771；辅助实验用2,000次、种子9133。

配对的意义是同一次采样里让两方案使用相同用户，保留“该用户改善还是退化”的对应关系。区间只描述当前协议和少量已有种子下的不确定性，不等于线上A/B保证。

### 9.2 归因边界

baseline到主方案同时改变：

1. 曝光+点击监督 → 仅点击监督。
2. 1个负例 → 64个负例。
3. 独立BCE分类 → 采样候选内InfoNCE竞争。

所以总体收益不能全部归因于“只改了一个loss”。开发中的 `click_bce64` 提供了相同点击监督、负例数量和采样规则下的更接近的对照；不同监督位置仍会改变实际计算量、随机数消费及优化路径。

确认规模每轮baseline监督19,199,815个位置，主方案监督2,050,483个位置。相同5轮不是等FLOPs。运行时间接近也不能证明计算量严格相同。

依据：[方案锁定](../reports/objective_study/model_selection.json)、[变体定义](../taac_retrieval/study.py)。

## 10. Faiss 检索工程

### 10.1 为什么需要索引

精确检索为每个查询扫描约270万条32维广告向量。它适合做模型效果参考，但真实推荐演示需要保存、重载索引并明确衡量近似损失与耗时。

当前工程链路：

```text
冻结checkpoint
 → 导出广告向量、查询、历史及身份信息
 → 构建/持久化索引
 → 验证集选择参数
 → 固定参数后测试
 → 推荐时编码q、检索、过滤、local映射OID
```

导出文件包含checkpoint摘要、缓存签名、维度、候选与ID规则。推荐时检查模型、导出向量和索引身份，避免用A模型的查询检索B模型的广告表示。

### 10.2 第一个问题：原始内积HNSW没有达到门槛

最初采用原始内积HNSW，`M=32`、`efConstruction=100`。验证中 `efSearch=1024` 的ANN重合率仅约 **84.84%**，没有达到预先设定的98%。

这不能简单通过“归一化成余弦”修复，因为主模型训练目标是原始内积，归一化会改变广告排序。继续增大搜索参数的诊断也没有消除主要差距，因此登记了检索几何修正。

原始失败记录保留在 [ann_initial_failure.json](../reports/objective_study/ann_initial_failure.json)。

### 10.3 MIPS→L2：改搜索几何，保留原始排序

令 `R²` 不小于所有广告向量平方范数，构造：

$$
v'_i=[v_i,\sqrt{R^2-\|v_i\|^2}],\qquad q'=[q,0].
$$

则：

$$
\|q'-v'_i\|^2=\|q\|^2+R^2-2q^\top v_i.
$$

固定查询下，右侧前两项不随广告变化，所以最小L2距离等价于最大原始内积。广告向量从32维升到33维，搜索距离再转换回原内积分数。

这是**对精确打分的等价变换**；HNSW仍是近似算法，是否改善近似质量需要实测。它不同于将向量归一化成余弦。

来源：[lift_database与InnerProductFromL2](../taac_retrieval/ann.py)、[修正登记](../reports/objective_study/ann_amendment.json)。

### 10.4 验证选参数

| efSearch | 验证ANN Recall@10 | 单查询p95，ms |
|---:|---:|---:|
| 128 | 87.2070% | 0.3113 |
| 256 | 92.1094% | 0.5108 |
| 512 | 95.1953% | 0.8802 |
| 1024 | 97.0898% | 1.6954 |
| 2048 | **98.2031%** | **3.7401** |
| 4096 | 99.0430% | 9.2948 |

选择满足98%门槛且验证p95最低的2048，而不是无条件选择重合率最高的4096。扩展参数搜索与几何调整都根据验证查询，未用测试结果反向选参数。

### 10.5 固定参数后的测试测量

使用**seed2026单模型、512个测试查询**：

| 项目 | FlatIP | MIPS-L2 HNSW |
|---|---:|---:|
| 维度 | 32 | 33 |
| 对同模型精确Top-10的重合率 | 100% | **98.8086%** |
| 单线程预热检索+历史过滤p95 | 40.1965 ms | **4.1443 ms** |
| 另一个8线程批量负载QPS | 188.8 | 2521.2 |
| 序列化索引大小 | 330.6 MiB | 1043.8 MiB |

索引设置 `M=32、efConstruction=100、efSearch=2048`，构建线程16。p95约加速9.70倍，但HNSW占用更大磁盘索引空间。

计时不含编码器、网络、启动及模型/索引加载；索引文件大小不是峰值RSS。QPS采用另一个批量、多线程负载，不能直接用p95倒数计算。共享工作站测量也不是生产SLA。

### 10.6 推荐出口与编号

主索引不存padding0，所以 `Faiss row0→local1`。检索时适当多取候选，过滤历史、无效项与重复项，最后通过 `catalog_oids[local]` 输出原广告OID。

`run_main.py --stage recommend` 是 Faiss 召回演示，按原内积分返回 Top-10。`--index` 表示固定评估队列中的位置。包含双通道与 DCN V2 的完整推荐使用[排序演示入口](ranking_extension.md)。

## 11. 冷启动与长尾诊断

### 11.1 先区分“少事件”与“少正目标”

按全部训练前缀事件数分桶，目录分布如下：

| 广告组 | 广告数量 | 占目录比例 | 训练点击总数 | 其中零训练点击广告数 |
|---|---:|---:|---:|---:|
| cold，0次 | 322,236 | 11.90% | 0 | 322,236 |
| tail，1～5次 | 1,931,099 | 71.31% | 383,774 | **1,583,588** |
| mid，6～50次 | 394,930 | 14.58% | 627,815 | 125,042 |
| head，大于50次 | 59,857 | 2.21% | 1,038,894 | 419 |

约 **82.00%的长尾广告没有训练点击**。它们可能在历史中出现、或作为负候选获得梯度，但缺少以这条广告自身作为点击正目标的直接监督。

头部广告只占目录约2.21%，却贡献约50.67%的点击正目标。这个不均衡说明不能只从Transformer层数判断冷尾问题，更需要检查训练信号分布。

均匀负采样下，每64个负例中长尾广告的期望数量约51.8；这描述了采样数量，不直接等于梯度占比，也不证明均匀负采样本身就是错误设计。

### 11.2 同是长尾，有没有点击支持也很不同

旧10,000人验证队列、三个原模型的平均Recall@500：

| 目标广告组 | 用户数 | Recall@500 |
|---|---:|---:|
| 长尾且没有训练点击 | 961 | 0.0694% |
| 长尾且有训练点击 | 365 | 2.4658% |
| 中频且没有训练点击 | 532 | 0.1253% |
| 中频且有训练点击 | 2,434 | 8.3265% |

这是相关性诊断；两组还可能有属性、频次和内容差异，不能直接当作点击监督的单因素因果实验。但它帮助把研究对象收窄到**零点击长尾**。

### 11.3 为什么不只给冷广告增加配额

旧开发诊断中，原主Top-500本来就有约30%的槽位是冷广告，冷目标仍很少命中。候选中“有很多冷广告”与“找到了正确的冷广告”不同。

同样，长尾占目录71%，不意味着推荐候选也应机械地分配71%给长尾。硬加配额可能把有效头部目标移走，必须实测新增与丢失。

### 11.4 固定查询的ID消融提供了什么线索

先不训练新模型，固定seed2026主模型的全部参数与查询，仅将零训练点击候选的显式ID贡献清零：

| 旧验证Recall@500 | 原表示 | ID消融后 |
|---|---:|---:|
| 整体 | 23.1200% | 21.2600% |
| 冷启动 | 8.4977% | 4.7041% |
| 全部长尾 | 0.5279% | 2.3379% |

961个零点击长尾目标从0个命中变为25个命中。它支持“部分长尾目标会受到当前独立ID分支影响”的假设，但整体新增35个、丢失221个，不能直接作为全局修复。

真正冷广告原本的ID就是0，消融不改变其向量和分数；但竞争广告的分数变化仍会把它挤出Top-500。**目标分数不变，不代表目标排名不变。**

这一步后来启发了辅助通道：保留原主列表，在专用子群中利用另一候选视图寻找新增，而不是整体替换评分。

诊断证据保存在 `research/content-retrieval:reports/coldtail_diagnosis/README.md` 及相关JSON；本地可用 `git show` 读取，命令见附录。

## 12. 辅助通道设计与实现

### 12.1 研究目标

在保留原主模型的条件下，是否能用很少的新候选补回一些零点击长尾目标，并把总体候选覆盖代价控制在预定范围？

这次不要求冷启动和长尾同时提高，也不要求辅助通道单独的整体效果超过主模型。评价对象是**融合后的候选增量**。

```text
用户信息＋可见历史 → 原冻结模型 → 同一个q
                                      │
                ┌─────────────────────┴────────────────────┐
                ↓                                          ↓
       原广告表示、原始内积                    显式ID置零的共享特征表示
                ↓                                  专用零点击长尾池
         原主Top-500                               过滤历史及主500
                │                                          ↓
                │                                  Top-25新提议
                └───────────── 固定预算保护融合 ─────────────┘
                                      ↓
                       原列表部分保留＋最多5个辅助项
                                      ↓
                            仍为500个互异候选
```

### 12.2 资格与两种广告视图

令 `n_i` 为训练事件数，`c_i` 为训练点击数：

$$
E=\{i\mid 1\le n_i\le5,\ c_i=0\}.
$$

本轮池内有 **1,583,588条广告**。真正冷启动广告 `n_i=0` 不属于该池；有点击长尾也不属于该池。

主候选仍使用：

$$
v_{\mathrm{main},i}=\operatorname{ItemEncoder}
(e_{\mathrm{ID},i},\mathrm{attributes}_i,m_{81,i}).
$$

辅助候选使用同一组参数：

$$
v_{\mathrm{aux},i}=\operatorname{ItemEncoder}
(0_{32},\mathrm{attributes}_i,m_{81,i}).
$$

ID输入仍占32维，因此融合层输入仍为480维；没有将网络改成448维。实现显式构造零ID块，不修改原Embedding表，也不修改历史编码。

所有原参数和查询均冻结，前后参数摘要核对一致。原高基数字段仍存在，所以称为“屏蔽显式ID的共享特征候选视图”，不能称为彻底去除身份信息的纯语义模型。

源码：[eligible_tail_ids与encode_tail_vectors，研究快照](tutorial_parts/tail_recall_snapshot/taac_retrieval/tail_channel.py)。

### 12.3 辅助评分只比较两种

$$
s_{\mathrm{raw}}(u,i)=q_u^\top v_{\mathrm{aux},i},
$$

$$
s_{\mathrm{cos}}(u,i)=
\frac{q_u^\top v_{\mathrm{aux},i}}
{\|q_u\|\,\|v_{\mathrm{aux},i}\|}.
$$

余弦归一化的是融合后的广告输出，不是对原始81再做一次无意义的归一化。它会改变辅助排名，作为一个小型评分对照；主通道仍保留原始内积。

实际开发选择了 `raw_ip`。归一化并没有在本轮带来更好的补尾表现。

### 12.4 必须在检索前排除历史和全部主候选

对用户 `u`：

$$
A_u=\operatorname{Top25}_{i\in E\setminus(H_u\cup M_u)}
s(u,i),
$$

其中 `H_u` 是可见历史，`M_u` 是原主500。

这里不是先全目录取500、再筛长尾；也不是先取25再删去重叠项。是在资格子集内，先屏蔽历史和主500，再得到最多25个真正新提议。

这样前1或前5个提议不会被已在主列表里的广告占用。计算遍历整个资格池，使用分块精确检索；目前没有持久化的辅助Faiss索引。

### 12.5 子集行号必须显式映射

假设辅助池的local ID为 `[35,90,110]`：

| 辅助矩阵行 | 真正local ID |
|---:|---:|
| 0 | 35 |
| 1 | 90 |
| 2 | 110 |

检索行1对应local90，不是 `1+1=2`。`retrieve_tail()` 使用升序ID和 `searchsorted` 找到屏蔽项，并在返回时通过 `ids[positions]` 还原local ID。

这是主完整索引与辅助子集检索在编号处理上的关键区别。

### 12.6 固定500预算的保护融合

保护集合：

$$
P_u=\operatorname{Top10}(M_u)\cup
\{i\in M_u\mid n_i\le5\}.
$$

选择实际替换数量：

$$
m=\min(\mathrm{quota},\mathrm{新提议数},\mathrm{可移除数}).
$$

从主列表尾部挑选不在保护集合中的 `m` 个位置删除，保留其他主候选的相对顺序，再追加前 `m` 个辅助提议：

$$
F_u=\operatorname{KeepOrder}(M_u\setminus D_u)
\;\Vert\; A_u[:m].
$$

`quota` 是上限，实际只比较1或5。最终仍为500个非padding、互异、未见广告。

保护规则意味着：

- 每人的原Top-10身份与顺序不变，因此HR@10、NDCG@10完全不变。
- 原有冷广告与两类长尾候选全部保留。
- 新增只能来自零点击长尾。
- 可能失去的目标来自未保护的中频、头部。
- 冷尾不下降来自结构约束，不是辅助网络新学到了冷启动能力。

源码：[retrieve_tail与fuse_tail，研究快照](tutorial_parts/tail_recall_snapshot/taac_retrieval/tail_channel.py)。

### 12.7 一个实际补回案例

以下来自锁定方案后的确认结果，目标只在检索完成后用于解读：

| 项目 | 数值 |
|---|---|
| 模型seed | 2026 |
| 内部用户行 | 253247 |
| 目标local ID / RID | 1326725 / 2343178 |
| 目标训练事件 / 点击次数 | 1 / 0 |
| 原主检索 | 前500之外 |
| 辅助新候选排名 | 第2 |
| 融合后排名 | 第497 |

删去5个未保护项后，原候选保留495个；辅助第2项进入 `495+2=497`。该用户的Recall@500从0变1，但HR@10仍为0。

同一用户还被另外两个模型补回，算3次“模型—用户”命中，仍只有1个不同用户。真实案例来自 [examples.json，研究快照](tutorial_parts/tail_recall_snapshot/reports/supplemental_tail_study/examples.json)。

点估计通过了登记的99%容忍门槛，但不等于总体业务价值提高。长尾新增用户少，区间触0，不能称为稳定或显著提升；当前离线抽样下整体覆盖损失较明确。

因此保留为**可解释的小型辅助召回实验原型**，没有默认接入主推荐链路，也没有继续利用这批确认目标调参。

依据：[完整指标快照](tutorial_parts/tail_recall_snapshot/reports/supplemental_tail_study/metrics.json)、[独立核验快照](tutorial_parts/tail_recall_snapshot/reports/supplemental_tail_study/verification.json)。

### 13.6 成本与实现边界

158万条32维float32辅助向量本身约193.3 MiB，还不包括local ID映射、模型、原特征、检索临时空间和潜在索引。

确认时batch=128，GPU精确子集检索均摊约0.268～0.294 ms/用户，包含过滤与结果传回CPU，排除向量编码、主检索和融合。它不是单请求p95，也不能直接与旧单线程CPU Faiss的4.14 ms比较。

目前辅助没有持久化索引或常驻服务。正式服务若要使用，需要另外验证索引身份、近似损失和端到端延迟；本轮结果没有覆盖这些内容。

## 14. 遇到的问题、尝试与处理

这里的“处理”既包括修复实现，也包括排除一个原因、改变研究问题或停止采用一个方案。不把所有失败改写成最终成功。

### 14.1 数据与检索工程

| 问题或明确风险 | 依据 | 处理 |
|---|---|---|
| 官方候选不能覆盖本地目标 | 覆盖审计 | 固定公开序列广告并集，注明静态目录假设 |
| 已曝光广告的后续点击会被历史过滤删除 | 切分与过滤的约束 | 留出窗口内首次出现点击，严格时间截断 |
| 空动作混入监督 | 原数据有null | 内部编码3，保留上下文、排除监督 |
| OID/RID/local/Embedding行混用 | 跨表编号不同 | 显式映射、缓存签名、产物身份校验 |
| 全目录分数矩阵占内存 | 用户batch乘270万广告 | 分块精确Top-K |
| 原IP-HNSW达不到98%门槛 | 实际验证失败 | MIPS→L2等价升维，再验证选参数 |
| 子集索引不能直接加1映射 | 辅助local ID不连续 | 保存显式local IDs并还原 |
| GPU参数直接转NumPy做摘要失败 | 辅助预检的设备接口错误 | parameter_hash改为detach().cpu().numpy() |

时间、ID和缓存检查是当前协议中的防范措施，不代表已经证明不存在所有其他偏差。参数摘要实现见 [研究runner快照](tutorial_parts/tail_recall_snapshot/scripts/run_supplemental_tail.py)。

### 14.2 全部事件InfoNCE-64与仅点击的补充对照

主方案选定后，又比较全部曝光+点击InfoNCE-64和仅点击InfoNCE-64。保持网络、每监督位置64负例、温度、5轮及超参数；未知和padding均不监督。

旧10,000人验证、三种子均值：

| 监督 | HR@10 | NDCG@10 |
|---|---:|---:|
| 仅点击 | 2.9733% | 0.015775 |
| 全部曝光+点击 | 2.9233% | 0.015133 |

全部减仅点击的NDCG差值区间为 [-0.003304,+0.001934]，跨0。后来重看旧测试时，全部事件均值略高，但方向与验证不同、区间仍跨0；不能把它当作新的独立确认或反过来作为最初选型依据。

不同mask改变监督总量及随机流消费，因此不是等总负例、等算力。结论是保留已确认的主方案，不宣称点击监督在任何设置下都更优。

证据：`research/supervision:reports/infonce_supervision/README.md`。

### 14.3 加深Transformer没有带来已确认的替代方案

固定旧验证队列、hidden32、heads1、点击InfoNCE-64、5轮及共享形状参数初始化，对比1/2/4层：

| 层数 | 验证NDCG@10 | 验证HR@10 | 整体Recall@500 | 冷Recall@500 | 尾Recall@500 |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.015775 | 2.9733% | 23.0600% | 8.3966% | 0.7290% |
| 2 | 0.016316 | 3.1067% | 22.5367% | 9.3576% | 0.6787% |
| 4 | 0.016498 | 3.1467% | 22.9733% | 9.1553% | 0.6787% |

4层相对1层的NDCG差值区间 [-0.000866,+0.002225]，没有独立测试确认，长尾覆盖没有改善。上述是各自按验证选最佳轮的成绩，不等于最后一轮也保持优势。

一层已有约1.296亿参数，主要来自Embedding；每增加一层只增加约6,464个参数。大ID表与深兴趣建模不是同一类容量，也不能从层数单独判断效果。

结论：保留容量对照，默认主模型仍为一层。

证据：`research/depth:reports/depth_study/README.md`。

### 14.4 早期ID遮蔽和内容融合

早期在历史、正候选和负候选上按广告身份共享随机ID掩码，3种子×5轮；推断关闭遮蔽。旧验证结果：

| 方案 | 整体Recall@500 | 冷Recall@500 | 尾Recall@500 |
|---|---:|---:|---:|
| 主模型 | 23.0600% | 8.3966% | 0.7290% |
| ID遮蔽30% | 23.9067% | 5.8675% | 0.6033% |
| ID遮蔽70% | 22.7667% | 5.9181% | 1.2318% |

70%模型的后续保护融合在旧验证曾得到冷覆盖9.2564%、尾覆盖0.9301%，但整体降至22.4167%。这只是旧验证开发结果，没有新确认，不能把此冷覆盖优势拼入最终辅助通道。

原始内容召回也出现“增加配额、损失有效主候选”的问题。保护原Top-10和已有冷尾可以防止特定桶退化，却不能保证有限配额内有新的正确目标。

证据：`research/cold-start:reports/cold_start/README.md`。

### 14.5 可训练内容通道为什么没有保留

后续训练两个不含广告ID/用户ID的内容模型：

| 方案 | 用户/广告结构 | 参数数 |
|---|---|---:|
| mm81 | 81、存在标志、用户属性、历史内容均值+MLP | 13,896 |
| side | 加低基数属性，排除102/121/122等高基数字段 | 93,096 |

各3种子、5轮，开发2,000人。开发没有方案通过门槛；按事先登记的失败确认规则，锁定mm81+配额25做一次10,000人负面证据确认，不应说开发已经通过。

那次确认整体Recall@500从23.2000%降到22.4267%，冷7.2322%、尾0.7048%保持；新增0/0/0，丢失79/80/73。

诊断与处理：

1. 完整内容列表里有互补目标，但没有进入前25个新提议，不能把潜在命中当实际融合收益。
2. raw81与学习内容候选集合不同，命中向量却相同；逐行重建确认不是误用同一个数组。
3. 新内容模型同时去掉原用户ID和Transformer，弱化了用户侧，失败不能全部归因于去广告ID。
4. mm81所有轮NDCG@10都为0，平局选了第1轮；事后重放看到Recall@500由0.25%升至0.75%，说明Top-10选模对候选覆盖不敏感，但仍不足以挽救该模型。
5. 重放中保存/恢复CPU与CUDA随机状态，避免额外诊断消费随机数而改变训练轨迹。

后续因此改为保留有效主查询、用覆盖目标选型、在专用子集内寻找新增，不根据已经看过的确认结果回头换epoch。

证据：`research/content-retrieval:reports/content_retrieval/README.md`、`analysis.md`、`candidate_audit.json`，以及 `reports/coldtail_diagnosis/README.md`。

### 14.6 点击支持门控与候选随机遮蔽

**点击支持门控**只把无训练点击候选的ID乘scale，历史ID保持完整。相同seed2026主checkpoint起点，重置Adam，lr0.0003、batch128、2轮，损失和64负采样不变。旧10,000人开发：

| 方案 | epoch | 整体Recall@500 | 冷Recall@500 | 尾Recall@500 |
|---|---:|---:|---:|---:|
| 原checkpoint | 0 | 23.1200% | 8.4977% | 0.5279% |
| 正常微调对照 | 2 | 23.6000% | 6.5250% | 1.0558% |
| scale0.5 | 1 | 25.1300% | 2.5797% | 1.8854% |
| scale0.5 | 2 | 24.7000% | 2.1244% | 1.8100% |
| scale0 | 1 | 25.4500% | 0.3035% | 1.5837% |
| scale0 | 2 | 25.4300% | 0.1517% | 1.4329% |
| scale0.75 | 1 | 24.3800% | 5.6146% | 0.9050% |
| scale0.75 | 2 | 24.5100% | 4.0971% | 1.2066% |

每个训练正目标必然有训练点击，门控主要直接改变的是零点击负候选。这可能造成弱ID与负例的关联，但没有被证明是唯一退化原因。微调会更新查询及共享特征参数，不能继续称为固定q。

长尾增长也主要来自有点击组：第二轮scale0/0.5/0.75的零点击长尾命中只有0/1/2个。

**标签无关候选遮蔽**随后另行登记：p=0.5，同广告在正负候选中共享掩码，历史不遮蔽，推断关闭遮蔽，不叠加门控。同样lr0.0003、2轮并复用正常微调对照：

| epoch | 整体Recall@500 | 冷Recall@500 | 尾Recall@500 | NDCG@10 |
|---:|---:|---:|---:|---:|
| 1 | 25.0200% | 4.0971% | 1.1312% | 0.015930 |
| 2 | 24.8600% | 3.4901% | 1.5083% | 0.015314 |

第二轮冷命中56→23，尾命中7→20，但零点击尾只从0→4；整体增长主要来自头部。

门控4次、候选遮蔽1次，各2轮，均未通过双参照保护门槛而停止，未复核其余种子、未打开新确认。最终辅助路线在它们失败后另行登记，改成不微调主模型、研究候选互补。

证据：[门控报告快照](tutorial_parts/tail_recall_snapshot/reports/click_support/README.md)、[候选遮蔽报告快照](tutorial_parts/tail_recall_snapshot/reports/candidate_regularization/README.md)。

### 14.7 哪些是实际修复，哪些只是研究判断

| 类别 | 结果 |
|---|---|
| 实现/工程修复 | 编号映射、缓存与索引身份校验、GPU参数摘要、分块搜索 |
| 经实测采用的主方案 | 点击InfoNCE-64、原IP语义下MIPS-L2 HNSW |
| 诊断线索 | 零点击长尾弱、固定q消融补回目标、内容选模指标不敏感 |
| 没有成为主方案的尝试 | 加深、ID遮蔽、内容学习、点击支持门控 |
| 最终辅助结论 | 有小规模互补，有整体代价，保留研究原型 |

停止一种方法，也是依照证据做出的决策；不能把所有阶段都写成连续上涨的模型升级。

### 16.4 常见追问与局限

**是不是双塔？**

主召回的打分可分离成用户与广告两侧向量，用户侧是序列 Transformer。主分支的辅助通道通过历史广告查同组内容。

**一层是否太简单？**
一层是当前确认过的选择。更深结构有旧验证对照，但区间跨0、长尾没有改善；大Embedding表也不等于深兴趣建模。

**为什么先检查覆盖再加排序？**

排序只能调整已有候选的位置。历史查组补入一些稀有目标后，原融合分把它们排在榜尾。当前排序实验因此固定候选并比较 DCN V2 的效果。

**早期 ID 遮蔽研究为什么保留主模型？**
全局ID消融已显示明显竞争代价。保留主模型的有效匹配，辅助仅在限定子群尝试另一视图。

**早期零点击尾实验的总体覆盖变化如何解释？**
是带代价的小规模候选补充，满足自定点估计门槛，不足以称为稳定总体改进，因此未默认启用。

**排序结果适用于什么范围？**

当前是静态目录的逐用户离线验证，排序只在固定 500 条的候选池内完成。线上流量与全局时间生产回测需要单独验证。

不能把四层验证、早期融合、主模型测试、索引延迟和最新辅助指标拼成一个同时具备的版本。项目深度来自问题、假设、实现与证据之间的对应。
