在历史链路里，召回内积已经给全目录的合法广告排了序，NDCG 可以评价这个顺序。现在有了下游排序，对召回而言，前 500 条里有没有目标更关键。只要候选集合不变，重排不会改 Recall@500；会改的是前十成员和先后顺序。

NDCG 也可以用于观察召回列表的顺序。例如只把前 100 条交给下游时，Recall@100 有更直接的意义。Faiss 与精确 Top-K 的列表重合率比较的是两个系统输出是否一致，是另一项指标，参见 Faiss 专题。

9.3 单目标时，为什么 HR 和 Recall 在同一个 K 上相等？

令 ru 为目标广告的一基排名，即第一名的 r=1，目标未返回时当作 r=∞。当前协议每个用户只有一个目标点击，定义指示函数 𝟙[条件]：成立时为 1，否则为 0。

HR@K = (1 / U) ∑u=1…U 𝟙[ru ≤ K]

HR 是“多少用户的目标进入了前 K”。标准 Recall 是“找回的相关项数 ÷ 全部相关项数”；这里每人恰好一个相关目标，所以单目标 Recall@K 与 HR@K 数值相同。Precision@K 的分母是推荐列表长度 K：一次命中时 Precision@10=1/10，并不等于 HR@10。

DCG@K = ∑j=1…K relj / log2(j+1)  ;  NDCG@K = DCG@K / IDCG@K

这里使用二元相关性：真实目标位置 rel=1，其他位置为 0。理想排序把唯一目标放在第一名，因此 IDCG=1/log₂(2)=1，公式化简为：

NDCG@K = (1 / U) ∑u=1…U gK(ru)，其中命中时 gK(r)=1 / log2(r+1)，未命中时为 0

9.4 怎样公平地比较两种排序？

让两种排序器处理每个用户相同的 500 条，都在同一个留出点击上算 HR@10 和 NDCG@10。项目的最终指标以整个评估队列为分母。目标不在 500 条里的用户仍计入，两个排序器在这些用户上都记 0。只看召回成功用户时，可以另外报告条件命中率：P(进前十 | 进入候选)，它不能拿来代替全队列 HR@10。

coverage_summary() 先找每个目标的名次，再针对 10、100 和 500 分别判断命中并计算位置折扣。召回或排序诊断都可以用它。分桶依据目标广告在全体用户训练前缀里的事件次数：冷启动 0 次、长尾 1～5 次、中频 6～50 次、头部超过 50 次。它包含曝光、点击与未知事件。

这一章的自测

固定候选后，DCN V2 让目标从第 11 名升到第 8 名，Recall@500 会变吗？

不会。目标一直在这 500 条里，变的是 Top-10 命中和位置折扣。若排序后 Recall@500 有变化，要先检查是不是比较了不同的候选集合。

目标排第 3 名时，为什么 NDCG 是 0.5？

唯一相关项的理想 DCG 为 1；实际折扣为 1/log₂(3+1)=1/2。若 K 小于 3 则目标被截断，NDCG@K 为 0。

当前用户从没见过某广告，就能把它归为 cold_0 吗？

不能。cold_0 要求它在所有用户的训练前缀中出现次数为零；当前用户未见只是历史过滤的条件。
